# Confirmed future-pay minimum storage boundary

Decision date: 27 September 2026

## Approved facts and scope

The Founder approved storage of customer-confirmed future-pay periods in the
existing owner/business/tax-year-scoped durable repository. The physical table
contains only its scope key plus:

- source identity;
- period start and end;
- expected gross pay;
- expected tax deducted; and
- server-recorded confirmation time.

It has no raw-document, payslip, free-text, provider, HMRC, inferred-pay or
forecast-pay column. The source identity uses the closed
`future-source:<opaque-id>` grammar. Multiple non-overlapping periods may share
one source/employment identity; their dated keys and derived evidence identities
remain distinct.

## Lifecycle and read boundary

The exact repository supports create/replace for one dated period, exact dated
deletion, and owner/business/tax-year reads. Each operation requires a current
externally verified repository authority and active owner-to-business
membership. Writes are blocked once local account erasure begins. A current
durable annual-position identity is required before a stored period can become
a forecast fact.

The paid forecast runtime can use only an exact provider bound to the same
repository. Stored rows are re-read after forecast composition; a concurrent
update or deletion suppresses the result instead of releasing stale facts.
Confirmation time is generated by the server repository, never accepted from
the browser or an injected provider. Period end is the conservative forecast
recognition date; no separate unapproved pay-date fact is persisted.

Local account erasure physically deletes these rows with manual PAYE and annual
position records, after the existing legal-hold and backup-expiry clearances.
The user foreign-key cascade also covers identity deletion. No claim is made
about production backups, a target datastore or retention beyond account
closure.

## Still prohibited or open

This boundary adds no raw upload, free text, inferred payroll, provider/HMRC
access, credential use, production deployment, default activation or release
authority. A customer-facing capture/edit journey, target-runtime evidence,
representative-user evidence and production retention/backup acceptance remain
separate gates.
